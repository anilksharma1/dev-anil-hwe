The setup: a legal matter lands with a huge corpus. Every file needs a decision — is there PII, how much, and where does it route. Doing that by hand is slow, expensive, and inconsistent. And the costliest mistake isn't over-flagging — it's *missing* a responsive file. pii_triage automates the first pass so reviewers spend their time only on the ambiguous middle.

The output is deliberately boring: one row per file, holding entity-type *counts* and a routing *label*. That feeds two deliverables — Table 1 for searchable files, and Table 2 for non-searchable files, which we sample, have humans review, and extrapolate. And the guarantee that shapes every design decision: we never store a PII value. We count occurrences into a set that's thrown away when the function returns. Only counts and labels survive. This is what lets us run it anywhere without creating a new data-exposure risk.
How it works

Every file runs one decision tree

file_path │ size > cap ───────────────────────────────► manual_oversize ▼ extract text + metadata (read-only, 25+ formats) │ unsupported / error / container / legacy ──► needs_parser · review_error · container_expand · convert_lane ▼ image-only? ── +OCR ─► Document Intelligence ─┐ no OCR ─► nonsearchable_sample ▼ detect entities by type (values discarded) ◄────────────────┘ ▼ classify ambiguity │ no signals ────────────────────────────────► likely_non_responsive │ strong id (SSN…) ─► skip LLM │ ambiguous ─► Azure OpenAI grades responsiveness ▼ route to a final lane spreadsheet ≥ threshold ─► structured_bde entities ≥ threshold ─────► bde entities < threshold ─────► standard

Early exits assign a lane and stop. The LLM is consulted only on genuinely ambiguous files — never when the answer is already clear. 10 lanes total.

Here's the whole engine on one slide. Every file walks the same tree. We short-circuit early: too big, unsupported, an archive, a legacy format — each gets its own lane and stops. If it's an image and OCR is on, we run Azure Document Intelligence; if OCR is off, it goes to the non-searchable sample. Then we detect entities — and immediately discard the values. Then the key move: we classify *ambiguity*. If there are no signals, it's non-responsive. If there's a strong identifier like an SSN, it's clearly responsive and we skip the LLM entirely. Only the genuinely ambiguous middle gets sent to Azure OpenAI for a graded call. Finally we route to a final lane. The whole point is: cheap, deterministic rules handle the clear cases; the expensive model only runs where it earns its keep.

Scale

Same engine, two ways to run it

Local — one machine
CLI, multiprocessing

python -m pii_triage scan /corpus …
The output CSV is the progress record — crash-safe resume, idempotent.

Scaled — Azure fleet
Container Apps + Storage Queue

~21 Linux workers poll a queue, one file each, autoscaling with queue depth. A Windows worker handles legacy Office (.doc/.xls/.ppt) via COM.

Built on scaling-lib — polling, retries, rate-limited AI clients, dead-lettering, status table, autoscaling. A matter is <job_dir>/files/ + a sibling protocol.pdf the workers pick up automatically.
The same code runs two ways. Locally it's a multiprocess CLI, and the neat trick is that the output CSV *is* the progress record — if it crashes, you re-run and it skips finished rows. At scale it's a fleet of Docker workers on Azure Container Apps, each pulling one file off a Storage Queue, autoscaling with the backlog. Legacy Office files that need Win32 COM conversion route to a dedicated Windows worker. All the plumbing — retries, rate limiting, dead-lettering, status tracking — comes from scaling-lib, so we don't reinvent it. And each matter is just a folder of files plus an optional protocol document the workers read automatically.
Why you can trust the numbers

Integrity is designed in, not asserted

Deterministic rules pass
byte-identical across runs

"Not measured" ≠ zero
a missing metric never shows as 0
Unrecorded values render as a dash — never a fake zero.
Read-only, everywhere
no file is ever modified
No writes to the corpus, no code execution, no network unless OCR/LLM is explicitly on.
Archive before destroy
reset verifies first
Clearing a run archives every job's rows and re-reads them to verify — or it refuses.

Tests: 111 on the core library · 46 on the UI · store flows validated end-to-end against a local Azurite stack.

This is the slide I care most about for a mixed room. Trust isn't a claim here — it's built in. First: the rules-based decision path is fully deterministic. A file that didn't need the model must produce a byte-identical row on every run, and we have a Compare screen that literally diffs two runs to prove no rules-decided row moved. Second: we rigorously distinguish "not measured" from zero — if the pipeline didn't record something, the UI shows a dash, never a misleading zero. Third: the whole thing is read-only — it never touches the corpus and makes no network calls unless you explicitly turn on OCR or the LLM. Fourth: the destructive "reset" operation archives and verifies before it clears anything. Backed by 111 core tests and 46 UI tests, plus end-to-end validation against a local Azure emulator.
Does it actually work?

We score every run against human review

The vs manual review step compares the pipeline's decisions to a reviewer's entity export and produces a full scorecard.

↓Missed notifications
% of cleared files that were actually responsive. The number we drive toward zero. Target < 5%.
↕Over-flagged
% of flagged files that were actually non-responsive — extra review cost. Target < 50%.
✓Recall · Precision · F1
Plus cost, timing, and per-entity-type breakdowns, all in one workbook.

"Read the misses first." The scorecard leads with the responsive files the pipeline cleared — the only error class that can hurt.

And crucially — does it work? We don't guess. Every run can be scored against a human reviewer's export. The scorecard leads with the number that matters: *missed notifications* — files the pipeline cleared that a human said were responsive. That's the asymmetric risk from slide two, and we drive it toward zero, targeting under 5%. We also track over-flagging, which is just wasted review cost, and the standard recall/precision/F1, cost, and timing. The design philosophy is "read the misses first" — we surface the dangerous errors before anything else.
